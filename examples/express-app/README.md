# example: express-app

> **Fixture, not production code.** A minimal Express server used to demonstrate the capwall
> observe→enforce loop. It exercises two real capabilities so capwall has something to see:
> appending to `./logs/requests.log` (`fs:write`) and reading `process.env` — both directly
> and through its dependency tree (`express`, `debug`, `depd`, `mime`).

## Walkthrough

```bash
pnpm install && pnpm build        # from the repo root, then cd examples/express-app

# 1. OBSERVE — nothing is blocked; capwall records what express + this app do and
#    emits a starter capabilities.json. Write it to a scratch file so the committed,
#    reviewed policy in this directory is not merged over (observe merges, not overwrites).
node ../../packages/cli/dist/index.js observe -o /tmp/observed.json -- node src/server.js
curl localhost:3000/              # exercise routes so they get observed
curl localhost:3000/log
# Ctrl-C the server → capwall writes /tmp/observed.json before exiting.

# 2. REVIEW — compare it against the committed policy and tighten. See "About the
#    committed policy" below: the observed output is a draft, not the answer.
diff <(jq -S . capabilities.json) <(jq -S . /tmp/observed.json)

# 3. ENFORCE — run for real under the committed policy; anything outside it is denied.
node ../../packages/cli/dist/index.js enforce -- node src/server.js
curl localhost:3000/log           # → "logged" — the granted write goes through
```

Under the committed policy, step 3 prints **no `DENY` lines at all**, and
`capwall diff -- node src/server.js` exits 0. That round-trip is a regression test
(`packages/cli/test/express-app-policy.test.ts`), so it cannot quietly stop being true again
— it did once, see issue #57.

If you delete the `./logs/requests.log` write grant from `capabilities.json` and hit `/log`
under enforce, capwall denies the write (deny-by-default) and the route 500s with a
`CapabilityError`. That is the mechanism the malicious-dep-demo leans on.

## About the committed policy

`capabilities.json` here is **generated by `capwall observe`, then hand-reviewed** — which is
step 2 of the loop, not a departure from it. Two of the three edits are the ordinary
tightening any reviewer does; the third is a genuine trade-off worth understanding before you
copy it.

| Package | Grant | Where it came from |
|---|---|---|
| `<app>` | `fs.write` on `./logs`, `./logs/requests.log` | observed, kept as-is |
| `express` | `env: NODE_ENV, NODE_CLUSTER_SCHED_POLICY` | observed; both come from express's own code (`app.set('env', …)`, and `listen()` reaching Node's cluster module) |
| `depd` | `env: NO_DEPRECATION, TRACE_DEPRECATION` | observed; both are read by name in depd's source |
| `mime` | `env: DEBUG_MIME` | observed; read by name in mime's source |
| `debug` | `env: ["*"]` | **hand-widened** — see below |

The hand edits were: dropping the ~85 host-specific keys attributed to `debug` in favour of
`"*"`, setting `"mode": "enforce"` (this is a reviewed policy, not a draft), and adding
`"$schema"` so editors validate it.

### Why `debug` gets `env: ["*"]`

`debug` builds its options object like this:

```js
Object.keys(process.env).filter((key) => /^debug_/i.test(key))
```

It only *uses* `DEBUG_*`, but capwall mediates the enumeration key-by-key, so `debug` is
recorded as reading **every variable present on the machine**. A raw `observe` run on a
developer laptop produced 84 keys for `debug` — `SSH_AUTH_SOCK`, `PYENV_ROOT`,
`GNOME_TERMINAL_SCREEN`, session-specific junk. Committing that list would break for the next
person and churn on every run. Running the same observe in a scrubbed environment
(`env -i PATH=$PATH HOME=$HOME PORT=3000`) yields a *different* 10-key list; with fake
credentials exported, `AWS_SECRET_ACCESS_KEY` and `GITHUB_TOKEN` show up in it too. The key
set is a property of the machine, not of the package — so no finite list is correct.

This is the same non-reproducibility that ephemeral ports created for `net.ports`, which was
resolved with the same `"*"` escape hatch (issue #27). Whether capwall *should* count
enumeration as a value read is a separate open question (issue #67); if that changes, this
grant should be narrowed back down.

**What that costs.** `debug` can now read any environment variable, including ones that do
not exist yet, and capwall will never report env drift for it again. That is a real
weakening: `env` is exactly where the token-stealing worms capwall is aimed at go looking.
What still contains it is everything else the policy withholds — `debug` has no `fs`, no
`net`, no `child_process`, no `worker_threads` grant, so it can *see* a token but has nowhere
to send it and no way to persist it. Deny-by-default on the other capabilities is doing the
work here; the `"*"` is affordable because of them, not instead of them.

In a real application, the honest options at this point are the same three, in order:
enumerate the concrete keys if they are stable; widen to `"*"` and rely on the remaining
capability limits; or decide the dependency does not belong in the production tree. This
fixture takes the middle one because it cannot take the third — `debug` arrives transitively
with `express`. `docs/policy-format.md` § `env` has the full guidance.

### Known limitation

Run this example with `DEBUG` **unset**. When `DEBUG` is set in the environment, `debug`
assigns back to `process.env.DEBUG`, and capwall's env proxy currently rejects writes to
keys that already exist (`ERR_INVALID_OBJECT_DEFINE_PROPERTY`). That is a shim bug, unrelated
to this policy — tracked separately in issue #66.
